# 08 템플릿 운영 규칙 (의사결정 기준)

목적: 누가, 어떤 모델이 작업해도 **같은 입력이면 같은 결과**, **같은 문제면 같은 진단과 같은 수정**이 나오게 한다.
판단이 들어갈 자리를 표와 알고리즘으로 바꾸고, 표에 없는 상황은 고치지 않고 사람에게 올린다.

관련 코드: `tools/marketing/template/` (`checks.py` 검사·보정, `render.py` `measure_slide`, `copy.py` 합성), `variations.py`, `video.py`.

---

## 1. 층과 수정 권한

| 층 | 위치 | 무엇이 들어 있나 | 누가 바꾸나 |
|---|---|---|---|
| 템플릿 | `templates/*.yaml`, `variations.py` 의 `STYLES`, `PALETTES`, `template/video.py` 의 `Motion` | 레이아웃, 크기, 배경 팔레트, 움직임. 앱 값과 문구는 `{{...}}` | **사용자 승인 후에만**. 트러블슈팅으로는 바꾸지 않는다 |
| 검사 기준 | `template/checks.py` 상수, 프리셋 `layout.*` 하한·상한 | 아래 3절 표의 기준값 | **사용자 승인 후에만** |
| 앱 프로필 | `apps/<id>.yaml` | 이름, 브랜드 색, 로고, 글꼴, 스크린샷 폴더, 화면 이름과 크롭 | 4절 규칙으로만. 규칙 밖의 값은 출처를 주석에 적는다 |
| 카피 | `copy/<id>.yaml` | 장별 문구, 쓸 화면 이름, 렌더 조합 | 사람 또는 LLM. 5절 규칙을 따른다 |

템플릿은 정적 데이터다. 앱이나 문구가 바뀌어도 템플릿 파일은 바뀌지 않아야 한다.

## 2. 결정성

- 렌더는 결정적이다. 같은 템플릿, 프로필, 카피, 스크린샷이면 같은 픽셀이 나온다 (2026-11-17 구조 변경 전후 `ig_carousel` 0번 장 픽셀 차이 없음으로 확인).
- 결과를 바꾸는 입력은 위 네 층과 스크린샷뿐이다. 스크린샷은 앱별 통합 테스트(`apps/<app>/integration_test/screenshots_test.dart`)로 다시 만든다.
- 보정 알고리즘(4절)도 결정적이고 멱등이다(결과를 넣고 다시 돌리면 같은 값). 섞기 단계는 10% 고정.

## 3. 자동 검사 (렌더할 때마다 `measure_slide` 가 낸다)

| 검사 | 지표 | 기준 | 근거 | 실패 시 (4절 규칙 번호) |
|---|---|---|---|---|
| 규격 | 크기, 용량, 형식, 알파 | 프리셋 `canvas` | 플랫폼 공식 규격 (05 문서) | 템플릿 문제. 사용자 보고 |
| 화면 노출 높이 | `visible_height_pct` | ≥ 60% | 우리 설정 | R3 |
| 화면 배율 | `min_screen_scale` | ≥ 0.5 | 우리 설정 | R4 |
| 화면 가로 노출 | `min_visible_width_pct` | ≥ 92% | 우리 설정 | R5 |
| 빈 구간 | `empty_band_pct` 보이는 부분에서 연속 빈 줄 비율 | ≤ 45% | 우리 설정 (7절 보정표) | R2 |
| 대비 | `contrast_headline/emphasis/body` | 큰 글자 3:1, 그 외 4.5:1 | WCAG 2.2 SC 1.4.3 AA. 큰 글자 = 24 CSS px 이상 또는 700 굵기 18.66 CSS px 이상 (캔버스 px ÷ density) | R1 |
| 강조 구분 | `emphasis_diff` 강조색과 제목색의 RGB 채널 최대 차 | ≥ 40 | 우리 설정 | 템플릿 문제. 사용자 보고 |
| 좌우 여백 | `side_margin_pct` 보이는 화면 좌우의 앱 배경색 띠 (카드 배경과 6 넘게 다른 단색 열) | ≤ 20% | 우리 설정 | 렌더러가 자동으로 걷어냄 (T3). 남으면 보고 |
| 초점 노출 | `focus_visible_pct` 통합 테스트가 남긴 핵심 위젯 사각형의 노출 | ≥ 95% | 우리 설정 | 렌더러가 자동으로 맞춤 (T4). 남으면 테스트의 초점 지정 확인 |
| 같은 화면 반복 | `repeat` 같은 카피 안에서 같은 화면의 재사용 | 초점 없으면 경고 | — | 렌더러가 초점 확대 (T5). 초점 없으면 카피에서 화면 교체 |
| 캡션 넘침 | `caption_used_pct` | ≤ 캡션 영역 | 우리 설정 | R6 |
| 기울기 | roll / yaw·pitch | ≤ 20도 / ≤ 40도 | 우리 설정 (관측은 16도 초과 구간까지만, raw/10) | 템플릿 문제. 사용자 보고 |
| 자리표시자 | 채워지지 않은 `{{...}}` | 0개 | — | 프로필이나 카피에 키 추가 |

"우리 설정"은 관측 근거가 없는 값이다. 바꾸려면 사용자 승인이 필요하다.

## 4. 수정 규칙 (경고 하나에 정해진 순서대로만)

각 규칙은 앞 단계부터 하나씩 적용하고 다시 렌더한다. 마지막 단계까지 해도 남으면 **멈추고 지표 값과 함께 사용자에게 보고**한다. 표에 없는 수정(눈으로 값 정하기, 템플릿 고치기)은 하지 않는다.

- **R1 대비**: 렌더러가 자동으로 처리한다 (T1). 경고가 나면 규칙 버그이므로 보고.
  1. 어두운 배경 강조색: 프로필 `brand.on_dark` 를 비워 두면 `normalize_profile` 이 만든다. primary 를 `#161616` 위 4.5:1 이 될 때까지 흰색 쪽으로 10%씩 섞는다.
  2. 장별 배경에 대해 `auto_contrast`: 제목·본문(중립색)은 미달이면 #111111 / #FFFFFF 중 대비가 큰 쪽, 강조색은 배경이 어두우면 흰색·밝으면 검정 쪽으로 10%씩 섞어 WCAG 기준을 맞춘다.
- **R2 빈 구간**
  1. `python3 -m template suggest-crop --app apps/<id>.yaml --screen <이름>` 결과로 크롭을 바꾼다.
     - 크롭이 화면 전체(높이 1.0)이면 `content_bbox`: 내용 타일 2개 이상인 첫 줄부터 마지막 줄까지 (위아래 1줄 여유).
     - 아니면 `slide_window`: 크롭 높이는 그대로 두고, 내용 타일이 가장 많은 세로 위치로 옮긴다 (동점이면 현재 위치에 가까운 쪽, 그다음 위쪽).
     - 결과를 다시 넣고 돌리면 같은 값이 나와야 한다 (멱등). luck_insight 3개 화면에서 확인.
  2. 그래도 남으면 카피에서 같은 장의 화면을 레지스트리의 다른 이름으로 바꾼다 (내용이 있는 화면으로).
  3. 레지스트리에 맞는 화면이 없으면 스크린샷 시나리오(통합 테스트)를 바꿔야 한다. 사용자 보고.
- **R3 노출 높이**
  1. 카피에서 같은 장의 화면을 레지스트리의 더 키 큰 크롭 이름으로 바꾼다.
  2. 없으면 프로필에 크롭을 추가한다. 높이는 노출 높이 60%를 넘는 최소값, 위치는 `suggest-crop`.
- **R4 화면 배율**
  1. 카피에서 화면 2개 나란히 배치(`screen: [a, b]`)를 1개로 줄인다.
  2. 남으면 보고. (`contain` 계열 스타일은 구조상 0.25~0.4 가 나온다. 스타일 선택 문제)
- **R5 가로 노출**: 템플릿의 `shifts` 값 문제다. 사용자 보고.
- **R6 캡션 넘침**: 카피 문구를 줄인다 (5절 길이 규칙). 글자 크기는 바꾸지 않는다.

## 4.1 렌더러 자동 규칙 (템플릿 층, 12회 개선 루프 결과)

화면 크롭은 렌더 때 아래 순서로 결정적으로 정해진다 (`layers.resolve_boxes`, 렌더와 검사가 같은 함수 사용).

| 번호 | 규칙 | 조건 | 동작 |
|---|---|---|---|
| T0 | 반복 확대 | 같은 화면을 다시 쓰는 장 + 초점 있음 | 초점 폭으로 자르고, 화면 영역을 채우는 높이로 초점이 가운데 오게 |
| T1 | 대비 | 항상 | R1 참조 (`checks.auto_contrast`) |
| T2a | contain 배율 하한 | fit=contain, 배율 < 0.5 | 하한 배율로 영역을 채우는 높이까지만 위에서부터 남김 (배율이 실제로 오를 때만) |
| T2b | crop_top 연장 | fit=crop_top, 카드가 캔버스 아래 끝에 못 미침 | 크롭 아래를 연장. 한도: 스크린샷 높이 10% 이상 연속 빈 줄 직전 |
| T3 | 앱 배경색 띠 걷기 | 보이는 부분의 좌우 앱 배경색 띠 > 20% | 띠를 걷어내고(1타일 여유) T2 를 다시 적용 |
| T4 | 초점 맞추기 | 초점이 보이는 부분 밖 | 가로는 초점 폭까지 되돌림, 세로는 크롭을 옮김 (스크린샷 끝이면 위를 잘라 짧게). 초점이 보이는 높이보다 크면 초점 안에서 내용이 가장 많은 창 |

초점은 앱의 스크린샷 통합 테스트가 `shot(tester, name, [Finder...])` 로 지정하고, 테스트 끝의 `binding.reportData` 로 드라이버에 보내 `<name>.json` 사이드카로 남긴다 (iOS 는 takeScreenshot args 미지원).

## 5. 카피 규칙 (LLM 이 쓰는 유일한 층)

- 사실만: 앱 화면이나 앱 데이터에서 확인되는 것만 쓴다. 후기, 수치 주장, 비교 금지.
- 말투: 프로필 `register` (honorific = 해요체).
- 길이: 한 줄 16자 안팎 (기존 카피 규칙). 제목 2줄 이하, 강조 `[[ ]]` 1곳은 현재 카피가 따르는 관행이며 확정 규칙은 아니다.
- 장 수: 템플릿 장 수와 같게. 다르면 렌더가 멈춘다.
- 앱 이름은 `{{app.name}}` 으로 쓸 수 있다.
- 현재 자동 검사는 장 수와 화면 이름 존재 여부뿐이다. 길이, 강조 개수, 사실 여부는 자동 검사가 없다 (8절 미결정 3번).

## 6. 새 앱 추가 절차

1. `apps/<app>/integration_test/screenshots_test.dart` 로 스크린샷을 찍는다 (`tools/marketing/assets/shots/<id>/ko`). flutter 가 iOS 네이티브 파일을 자동 수정하면 되돌린다.
2. `apps/_template.yaml` 을 복사해 프로필을 만든다. 화면은 먼저 크롭 없이(전체) 등록하고, 렌더 경고가 나면 R2 의 `suggest-crop` 값으로 바꾼다. `on_dark` 는 비워 둔다.
3. `copy/<id>.yaml` 을 5절 규칙으로 쓴다.
4. `python3 variations.py --app <id>` 로 렌더하고, 경고를 4절 규칙으로만 처리한다.

## 7. 보정 기록

빈 구간 기준 45% 는 아래 9개 사례로 정했다. 표본이 2개 앱 9개라 기준이 바뀔 수 있다.

| 사례 | 빈 구간 % | 판정 |
|---|---|---|
| world_of_beast 지도, 위쪽 크롭 [0,0,1,0.6] (지도가 안 보였던 사례) | 52.9 | 경고 대상 |
| daily_memo 추가 화면 전체 (아래 절반이 빈 화면) | 50.0 | 경고 대상 |
| world_of_beast 지도, suggest-crop [0,0.32,1,0.62] | 34.6 | 통과 |
| world_of_beast 지도 전체 | 32.9 | 통과 |
| world_of_beast 상세 위쪽 | 26.5 | 통과 |
| daily_memo 추가 화면 위쪽 | 25.6 | 통과 |
| daily_memo / world_of_beast 목록 위쪽 | 9.4 | 통과 |
| daily_memo 저장 후 목록 | 3.4 | 통과 |

처음 시도한 '내용 타일 비율' 지표는 빈 지도(14.4%)와 정상 입력 화면(15.7~19.8%)이 겹쳐 구분하지 못해 기준에서 뺐다 (지표로만 남김).

이전에 눈으로 정했던 값의 처리:
- world_of_beast 지도 크롭 [0,0.36,1,0.66] → `suggest-crop` 결과 [0,0.32,1,0.62] 로 교체.
- world_of_beast `on_dark` #7FB6E6 → 규칙 값 #6D8CA6 (대비 5.13:1) 으로 교체.
- daily_memo 의 크롭들(목록, 추가, 저장 후)은 눈으로 잰 값 그대로다. 빈 구간 검사는 통과했지만 규칙으로 다시 구하지는 않았다.

## 8. 미결정 (사용자 결정 필요)

1. ~~**기존 템플릿의 대비 실패**~~ → 개선 루프 1·2회차에서 (b) 템플릿 글자색 규칙으로 처리 (T1). 아래는 당시 기록. 자동 검사를 켜자 daily_memo 23개 조합에서 35건이 나왔다.
   - 파스텔 배경 위 강조색 #C7870A: 2.44~2.75:1 (< 3:1), 28건
   - 노란 배경(#FFC107) 위 본문 #5A5A5A: 4.23:1 (< 4.5:1), 7건
   - world_of_beast 는 text_only 스타일에서 남색 배경(#0B3F6A) 위 검은 제목이 8건, 본문 5건.

   선택지는 두 가지다.
   - (a) 프로필 강조색을 규칙으로 어둡게 보정해 템플릿이 쓰게 한다 (`ensure_contrast`, 검정 쪽으로 10%씩).
   - (b) 템플릿의 글자색 규칙을 바꾼다 (배경 밝기에 따라 흰 글자 또는 검은 글자).

   둘 다 기존 결과물의 색이 바뀐다.
2. **"우리 설정" 기준값**: 노출 60%, 배율 0.5, 가로 92%, 빈 구간 45%, 기울기 20도와 40도를 확정할지.
3. **카피 자동 검사**: 길이, 강조 개수를 경고로 만들지.

## 9. 앱별 검증 기록 (템플릿이 충분한지)

| 앱 | 화면 형태 | 규칙만으로 해결 | 남은 경고 | 검사가 못 잡은 문제 (눈으로 확인) |
|---|---|---|---|---|
| daily_memo | 목록 + 입력 폼 | — | 대비 35, 배율 13 (contain 계열) | 없음 |
| world_of_beast | 목록, 상세, 지도 | 지도 빈 구간 (R2 slide_window) | 대비 13, 노출 18, 배율 3 | 상세 화면이 앱 자체로 비어 있음 |
| luck_insight | 화면 가운데 카드 1장, 아래쪽 시트 | 빈 구간 64건 → 0건 (R2 content_bbox) | 대비 54, 배율 8 | 아래 G1~G3 |

luck_insight 에서 드러난 템플릿의 빈틈 (2026-11-17, 30개 조합 렌더):
- **G1 이중 테두리**: 앱 화면 자체가 가운데 흰 카드라서, 우리 흰 카드 안에 앱 배경색 띠와 앱 카드가 한 번 더 보인다. 검사 항목 없음.
- **G2 핵심 요소 위치**: 1등 기록 화면의 핵심(아래쪽 시트)이 `crop_top` 배치에서 잘려 어둡게 덮인 카드만 보인다. 빈 구간 검사는 통과한다. 템플릿에 "어디가 중요한지(초점)" 개념이 없다.
- **G3 화면 수**: 앱 화면이 3장뿐이라 4장짜리 카피에서 같은 결과 화면이 두 번 나온다. 템플릿이 확대 크롭으로 변화를 줄 규칙이 없다.
