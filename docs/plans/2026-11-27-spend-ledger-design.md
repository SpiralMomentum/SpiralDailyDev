# 지출 위젯 가계부 (spend_ledger) 설계

- 작성일: 2026-11-27
- 원본 요구사항: `doc/26_Q4/가계부.md` (v0.2)
- 상태: 승인 (2026-11-27, 사용자: "앱 개발만 해")

## 1. 의도

이 앱은 지금 쓰는 가계부 앱의 두 가지 문제를 해결한다.

1. 선불 머니 자동충전, 송금, 환불 때문에 지출이 실제와 다르게 잡힌다.
2. 자동 연동 가계부에는 이번 달 총지출을 보여 주는 홈 화면 위젯이 거의 없다.

결제 문자를 자동으로 받아 한 달 지출을 정확히 집계하고, 앱을 열지 않아도 위젯에서 확인하게 한다. 사용자 본인이 매일 쓸 도구이므로 정확성(집계 규칙)과 마찰 없는 확인(잠금화면 알림, 위젯)이 성공 기준이다.

## 3. 제약

- Flutter 3.41.2 / Dart 3.11.0. build_runner가 이 환경에서 동작하지 않으므로 코드 생성(freezed, drift, json_serializable, mockito)을 쓰지 않는다. 모킹은 mocktail을 쓴다.
- 저장소 규칙: `lib/app` + `lib/features/<feature>/{domain,data,presentation}`, 상태 관리는 bloc/cubit, DI는 get_it (`doc/Coding/Architecture/*`, `doc/Coding/View/bloc_guideline.md`)
- 함수형 스타일: 도메인 로직은 순수 함수와 불변 값으로 작성하고, 부수효과는 data 계층에 둔다.
- iOS 위젯(WidgetKit)과 App Intent는 Swift 네이티브 타깃이 필요하다. 이 저장소에는 iOS 위젯 확장을 쓰는 앱이 아직 없다(`apps/*/ios`에서 WidgetKit 사용 0건).
- 최소 버전(내 결정): iOS 17, Android minSdk 26. iOS 17은 단축어 메시지 자동화 '즉시 실행'과 인터랙티브 App Intent 실행을 전제로 잡았다.
- 외부 유료 API 금지, 네트워크 권한 불필요.
- 배포: 본인용. Xcode/flutter run으로 직접 설치한다. 스토어 등록, CI(release-all.yaml) 등록, 개인정보처리방침, Play 정책 고지는 범위 밖이다(사용자 결정).
- 파서 픽스처: 실제 문자 샘플 없이 공개된 카드사·은행 문자 형식으로 만든다(사용자 결정). 실제 형식 차이는 파싱 테스트 화면(FR-23)과 형식 학습(FR-22)으로 보완한다.

## 4. 접근 방식 (사용자 선택 완료)

| 안 | 내용 | 트레이드오프 |
|---|---|---|
| **1. 코어 + iOS 프로토타입 병행 (선택)** | 플랫폼 무관 Dart 코어(파싱·집계·후보·앱 화면)를 먼저 만들고, 같은 시기에 iOS 수집 경로(단축어 → App Intent → 알림)를 최소 구현해 실기기로 검증 | 가장 큰 위험(원본 7절)을 일찍 확인한다. 실기기 검증은 사용자가 해야 한다 |
| 2. 코어 + Android 먼저 | Android 수집·위젯까지 완성 후 iOS | 진척이 빠르지만 'iOS 필수' 전제가 끝까지 미검증 |
| 3. 전체 동시 | 문서 전체 일괄 | 범위가 커서 중간 확인 지점이 없다 |

선택 이유: iOS 수집이 안 되면 제품 전제가 무너지므로, 그 확인을 코어 개발과 병행한다.

## 5. 단계

- **1단계 (이번 계획 범위)**: Dart 코어 전체 + 앱 화면 + iOS 수집 프로토타입
- **2단계**: Android 알림 리스너 수집 + Android 위젯(소/중/대) + 확인 알림 액션
- **3단계**: iOS 위젯(소/중/대/잠금화면) + 1단계 프로토타입 결과 반영한 iOS 수집 정식화 + 공유 시트 입력(FR-04) + 단축어 설치 링크(FR-02)

1단계 프로토타입 결과가 '불가'로 나오면 2단계 진입 전에 사용자와 iOS 방향을 다시 정한다.

## 6. 아키텍처

앱 위치: `apps/spend_ledger`, 번들/패키지 ID `com.spiralmomentum.spendLedger`, 표시 이름 '지출 위젯'(가칭, 내 결정).

```
수집(iOS App Intent / Android 리스너 / 공유 시트 / 수동 붙여넣기)
   └─ 원문 텍스트 + 발신자 + 수신 시각
        └─ ingest(): 필터 → 파싱 → 분류 → 중복/취소 매칭 → 저장 → 확인 알림
                                                          └─ 위젯 페이로드 갱신
```

모든 수집 경로는 같은 Dart 진입점 `ingestMessage(RawMessage)`로 모인다. 네이티브 쪽은 텍스트를 넘기는 일만 한다(파싱 규칙 단일화, FR-03 '파싱 규칙은 iOS와 같다').

| `parsing` | 범용 파서(FR-20, 21), 형식 학습(FR-22), 파싱 테스트 화면(FR-23) |
| `ledger` | 거래 저장, 분류·집계 규칙(FR-40~45), 후보 리스트(FR-32, 33), 수정 화면 |
| `budget` | 기간 시작일(FR-60), 예산·초과 예측 알림(FR-61), 요약 계산 |

### 6.2 도메인 모델 (불변 값)

- `RawMessage { text, sender?, receivedAt, source(ios_shortcut|android_sms|android_app|share|manual) }`
- `ParsedMessage { amount?, counterparty?, occurredAt?, kind(approval|withdrawal|transfer|cancel|refund|unknown), signature }`
- `Transaction { id, amount(원, 정수, 부호 있음), counterparty, occurredAt, kind, category(spend|prepaidCharge|transferOut|internal|prepaidUse|refund|unknown), status(pending|included|excluded|duplicate|cancelled), linkedId?, rawText?, needsReview }`
- `SummaryInput/LedgerSummary`: 기간 합계, 오늘 합계, 예산 비율, 하루 권장액, 경과 비율, 상위 3 가맹점, 최근 3건, 대기 후보 수

합계 = `status == included`인 거래의 `amount` 합. 위젯과 앱 화면은 같은 `summarize()` 순수 함수 결과를 쓴다(NFR-03).

### 6.3 범용 파서 (FR-20, 21)

카드사별 템플릿 없이 아래 규칙만 쓴다.
- 금액: `([0-9]{1,3}(,[0-9]{3})+|[0-9]+)\s*원` 매칭 중 '잔액/누적/한도/잔고'가 바로 앞(같은 토큰 또는 직전 토큰)에 붙은 것을 제외하고 첫 번째 값
- 종류: 키워드 사전. 취소(`취소`), 환불(`환불`), 출금(`출금`, `자동이체`), 송금(`송금`, `이체`, `보냄`), 승인(`승인`, `결제`, `사용`), 없으면 금액이 있을 때 `approval`로 추정(검증 기준 5: '승인'이 없는 문자도 알림)
- 일시: `MM/DD HH:mm`, `MM.DD HH:mm`, `MM월 DD일` 등 패턴. 없으면 수신 시각
- 가맹점·상대: 금액·일시·카드명·`[Web발신]`·마스킹 번호(`*`)·키워드 토큰을 제거한 뒤 남은 줄 중 가장 긴 한글/영문 토큰 줄. 송금은 '님', '에게' 앞 이름
- `signature`: 숫자 → `#`, 금액 위치 → `{A}`, 추출된 가맹점 → `{M}`으로 치환한 형식 문자열. 형식 학습 키

**형식 학습 (FR-22, 내 결정)**: 사용자가 가맹점이나 금액을 고치면, 원문에서 정답 값이 위치한 줄 번호·토큰 범위를 `signature`와 함께 저장한다. 다음에 같은 `signature`가 오면 저장된 위치를 우선 적용한다. 저장은 로컬 DB.

### 6.4 분류 규칙 (FR-40~45)

등록 이름 3종(내 결정: 원본 FR-12의 '충전처'를 두 용도로 나눔. 이유는 아래 표 참고):
- **내 이름** (FR-11): 본인 예금주명, 계좌 별칭, 카드사명
- **충전처** (FR-12): 출금·이체 상대가 이 이름이면 선불 충전 (예: `쿠페이`, `쿠팡페이`)
- **선불 머니 결제 수단** (FR-12 확장): 승인 문자 본문에 이 이름이 있으면 머니 사용 (예: `쿠페이머니`)

| 파싱 종류 | 조건 | category | 합계 반영 |
|---|---|---|---|
| approval | 본문에 선불 머니 이름 포함 | prepaidUse | 제외 (FR-41) |
| approval | 그 외 | spend | 포함 대상 (FR-40) |
| withdrawal/transfer | 상대가 내 이름 | internal | 제외 (FR-43) |
| withdrawal/transfer | 상대가 충전처 | prepaidCharge | 포함 대상 (FR-41) |
| withdrawal/transfer | 그 외 | transferOut | 포함 대상 (FR-42) |
| cancel/refund | — | refund | 자동 처리 (아래) |
| unknown 또는 금액 없음 | — | unknown, needsReview | 후보 '확인 필요' (FR-33) |

카드사 이름만 '내 이름'에 등록하면 카드값 결제 출금(상대 `OO카드`)이 internal로 빠진다. 단, 카드 승인 문자의 카드사명은 상대가 아니므로 영향이 없다(상대는 가맹점 추출 결과).

- '포함 대상' 거래는 `pending`으로 저장하고 확인 알림을 보낸다. 사용자가 '포함'을 누르면 `included`, '제외'면 `excluded`. 응답 없으면 `pending` 유지(FR-32).
- prepaidUse와 internal은 `excluded`로 바로 저장하고 알림을 보내지 않는다(내 결정: 확인할 필요가 없는 건으로 알림 피로를 줄임). 후보 리스트의 '자동 제외' 탭에서 볼 수 있고 포함으로 바꿀 수 있다.
- **중복 (FR-45)**: 수신 시각 기준 5분 안에 금액과 가맹점이 같은 거래가 있으면 새 건을 `duplicate`로 저장, 알림 없음.
- **취소·환불 (FR-44)**: `included` 또는 `pending` 거래 중 금액과 가맹점이 같고 시각이 앞서는 가장 최근 1건을 찾아 `cancelled`로 바꾼다. 찾지 못하면 음수 금액 거래를 `pending`으로 저장하고 알림("환불 -N원을 반영할까요?")을 보낸다. 부분 환불(금액 불일치)은 음수 거래로 처리(내 결정). 선불 머니 결제(prepaidUse) 건도 매칭 대상에 넣는다. 매칭되면 `cancelled`로 바꾸되 합계에는 변화가 없다. 돈이 머니 잔액으로 돌아온 것이고 충전 시점에 이미 집계됐기 때문이다(내 결정). 본문에 선불 머니 이름이 있는 취소 문자는 원거래를 못 찾아도 음수 거래를 만들지 않고 `excluded`로 저장한다.
- 가맹점 비교는 공백 제거·소문자화 후 포함 관계로 본다(내 결정, 문자마다 가맹점명 잘림 길이가 다르기 때문).

### 6.5 필터 (FR-10)

규칙: `{ senderPattern?, includeKeywords[], excludeKeywords[] }`. 제외 키워드가 하나라도 있으면 버림. 포함 키워드가 있는 규칙은 하나라도 매칭되어야 통과. 기본값(내 결정): 포함 `승인, 결제, 출금, 이체, 송금, 취소, 환불`, 제외 `누적, 결제예정, 광고, 인증번호`. 금액이 없어도 포함 키워드에 걸린 문자는 FR-33에 따라 후보로 남긴다. 필터에서 버린 문자는 저장하지 않는다.

### 6.6 예산·기간 (FR-60, 61)

- 시작일 1~31. 해당 달에 그 날이 없으면 말일(내 결정).
- 하루 권장액 = max(0, 예산 − 기간 합계) / 오늘 포함 남은 일수
- 초과 예측 = 기간 합계 / 경과 일수 × 전체 일수 > 예산이면 기간당 1회 알림, 실제 초과 시 1회 추가 알림.

### 6.7 저장 (NFR-01)

- `sqflite_sqlcipher` 암호화 DB. 키는 첫 실행 때 무작위 32바이트로 만들어 `flutter_secure_storage`(iOS Keychain, Android Keystore)에 둔다.
- 원문 삭제 설정(기본 켬): 거래가 `included/excluded`로 확정되면 `rawText`를 지운다. 형식 학습 데이터에는 원문이 아니라 `signature`와 위치 정보만 저장한다.
- iOS에서 위젯 확장과 App Intent가 같은 데이터를 보려면 App Group 컨테이너가 필요하다. 위젯에는 DB가 아니라 요약 페이로드(JSON)만 공유한다(home_widget). 금액 숨김(FR-55)이 켜져 있으면 페이로드에서 금액 필드를 비운다.
- 분석·크래시 SDK를 넣지 않는다.

### 6.8 확인 알림 (FR-30, 31)

`flutter_local_notifications`의 액션 버튼('포함', '제외')을 쓰고, 백그라운드 응답 핸들러에서 DB 상태 변경과 위젯 갱신을 한다. 본문 탭은 수정 화면 딥링크. 문구: "{가맹점}에서 {금액}원 지출이 있었던 것 같아요. 지출에 포함할까요?"

### 6.9 앱 화면

1. 홈: 이번 달 합계, 예산 비율, 오늘 지출, 하루 권장액, 진행 막대, 대기 후보 배지, 최근 거래
2. 후보 리스트: 탭 '확인 대기 / 확인 필요 / 자동 제외·중복'. 항목별 포함·제외, 탭하면 수정
3. 거래 수정: 금액, 가맹점, 일시, 분류. 저장 시 형식 학습
4. 설정: 기간 시작일, 예산, 필터 규칙, 등록 이름 3종, 원문 삭제, 금액 숨김, 파싱 테스트(FR-23), 단축어 설정 안내(FR-02)

디자인은 구현 단계에서 정한다(시각 결정은 빌더에게 위임, 단 위젯·홈은 같은 수치를 같은 포맷으로 보여야 함).

## 7. 1단계 iOS 수집 프로토타입

**확인할 질문 (원본 7절)**
1. 단축어 메시지 자동화 '즉시 실행'이 현재 iOS에서 확인 창 없이 돌아가는가
2. 단축어 → App Intent 실행이 앱을 화면에 띄우지 않고 끝나는가
3. App Intent 안에서 헤드리스 FlutterEngine으로 Dart `ingestMessage`를 실행해 3초 안에 알림을 띄울 수 있는가
4. 잠금화면에서 알림 '포함' 액션이 앱을 열지 않고 DB에 반영되는가

**구현**: Runner 타깃에 `RecordPaymentMessageIntent(text: String, sender: String?)` (`openAppWhenRun = false`). `perform()`에서 헤드리스 FlutterEngine을 띄워 Dart 진입점 `@pragma('vm:entry-point') iosIngestMain`을 실행하고, MethodChannel로 텍스트를 넘긴 뒤 완료 응답을 기다린다. 각 단계 소요 시간을 로그로 남기고 앱의 '진단' 화면에 표시한다.

**대체안 (질문 3이 실패할 때)**: App Intent가 원문을 App Group 수신함에 저장하고, Swift에서 금액만 정규식으로 뽑아 "N원 결제 문자가 왔어요" 알림을 보낸다. 분류와 저장은 앱을 열 때 Dart가 처리한다.

**사용자가 할 일**: 실기기 설치, 단축어 자동화 생성(안내 화면 따라), 결제 문자 수신 또는 자기 자신에게 테스트 문자 보내기, 진단 화면 결과 공유.
